* Foundations of Computer Science for Staff-Level Engineering
Twelve files that cover the theory and systems fundamentals behind senior engineering decisions, plus this guide. Follow links with =C-c C-o= (cursor on the link) and return with =C-c &=.

** Scope and expectations
- *What these notes are*: a technical-foundations curriculum: mathematics, algorithms and data structures, computability and complexity, programming-language theory, memory, concurrency and distributed systems, and data representation. Each file states the Staff-level use of its topic, explains the ideas, runs the code, and ends with self-checks, exercises, and sources.
- *What they are not*: a promotion plan. Staff-level work is mostly a matter of scope, judgment, influence, and writing, which these files do not teach. The StaffEng project describes how the role works, including the common archetypes (Tech Lead, Architect, Solver, Right Hand): [[https://staffeng.com/guides/][staffeng.com/guides]] and [[https://staffeng.com/book][the book]]. Strong foundations make your decisions better and your arguments defensible; they do not replace the rest.
- *Calibrating depth*: the goal is to explain, apply, and critique each topic, to know where the sharp edges are, and to know which primary source to open next. It is not to memorize results.

** How to use these files
1. Read in the order below. Earlier files give vocabulary the later ones assume.
2. Work through each file in four passes: read, run the code, do the exercises, answer the self-check questions without notes.
3. Keep an engineering notebook: for each file, write a one-page summary in your own words and one real example from your work where the topic mattered (an incident, a design choice, a review comment).
4. Use the capstone projects (below) to integrate several files; they are the best evidence that you can apply the material.
5. Read the primary sources listed in each file for at least one topic per file. The notes summarize; the sources are the authority.

*** Running the code blocks
The Python blocks are self-contained and end in assertions: a block that finishes silently has passed. They were run on Python 3.12. The C block in the memory file was compiled with GCC. The Lean snippets and the =text= blocks (pseudocode, Haskell) are illustrative and were not executed here; check the Lean ones in your own installation.

#+begin_src sh
# add to your shell config: run every Python block of an org file, reporting failures
orgpy() {
    python3 - "$1" <<'PY'
import re, subprocess, sys, tempfile, os
text = open(sys.argv[1]).read()
blocks = re.findall(r'#\+begin_src python\n(.*?)#\+end_src', text, re.S)
bad = 0
for i, code in enumerate(blocks, 1):
    with tempfile.NamedTemporaryFile('w', suffix='.py', delete=False) as t:
        t.write(code)
    r = subprocess.run([sys.executable, t.name], capture_output=True, text=True, timeout=120)
    os.unlink(t.name)
    if r.returncode:
        bad += 1
        print(f'block {i} FAILED:\n{r.stderr}')
print(f'{len(blocks)} python blocks, {bad} failed')
PY
}

orgpy 06_algorithms.org
#+end_src

** Reading order and rationale
The order follows dependencies and moves from abstract tools to machine realities:
- *Mathematical core (01, 02)*: counting, probability, number theory, graphs, logic, and proof. Everything quantitative or rigorous later uses them.
- *Representation first (03)*: bits, numbers, text, and encodings make the machine concrete early and feed hashing, layout, and cost.
- *Analysis and structures (04, 05, 06)*: cost models, data structures, then algorithms that use them.
- *Limits of computation (07)*: what cannot be computed or analyzed, and the formal languages behind parsers.
- *Languages and types (08, 09, 10)*: paradigms, functional programming, and type systems; they share the lambda calculus and logic.
- *Machines and systems (11, 12)*: memory management, then concurrency and distributed systems, which need ownership, memory models, and invariants from the earlier files.
Skipping around is fine if you already know a topic; do the self-check first, and read only the sections you cannot answer.

** A checklist of Staff-level technical judgment
Rate yourself honestly; the items are skills, not facts.
- [ ] I can state the invariant and the failure model of a system I own, and I know which of them are tested, which are modeled, and which are assumed.
- [ ] I can estimate the cost of a design (time, memory, network, tail latency) from first principles, and I know which constants matter at our scale.
- [ ] I recognize hard problems (NP-hard, undecidable, distributed-consensus) disguised as product requirements and propose workable alternatives.
- [ ] I choose data structures and storage layouts from the workload and the memory hierarchy, and I can explain the trade-off to a peer.
- [ ] I can read and review concurrent code, protocols, and database transactions for races, deadlocks, and consistency anomalies.
- [ ] I design APIs and types that make misuse hard, and I can explain the soundness gaps of the type systems I rely on.
- [ ] I choose languages and paradigms for stated reasons, and I write the decision down with alternatives and reversal costs.
- [ ] I diagnose memory and performance problems with measurements and a correct mental model of caches, GC, and allocators.
- [ ] I encode data so that it survives schema evolution, language boundaries, and time zones.
- [ ] I can teach any topic in these files to a colleague using an example from our own systems.

** Coverage against a standard curriculum
The ACM, IEEE Computer Society, and AAAI /Computer Science Curricula 2023/ report organizes the discipline into knowledge areas with units and learning outcomes: [[https://csed.acm.org/wp-content/uploads/2024/05/The-Report.pdf][the report (PDF)]]. These notes concentrate on the foundations most relevant to senior engineering: algorithms and complexity, mathematical foundations, programming-language foundations, systems fundamentals and memory, parallel and distributed computing, and data representation. They do not cover databases, networking, security, graphics, human-computer interaction, machine learning, or software-engineering process in depth; use the report's unit lists to find the gaps relevant to your work.

** Provenance and limits
- The files were written from the sources above and from standard textbook knowledge. Source pages were located and their scope checked; they were not all read cover to cover, and specific figures in the notes (latency orders of magnitude, industry statistics, library behavior) are conventional or approximate. Verify any number you depend on against a primary source.
- Python code was executed (all assertions pass) and the C snippet was compiled and run; Lean and pseudocode were not executed.
- Results are stated at textbook level. Where research is moving (garbage-collector designs, consensus variants, type-system features), treat the notes as a map and the papers as the territory.
- When you find an error, fix the file and note the source of the correction at the bottom of the relevant section.

** A suggested cadence
As a rough guide only (it depends heavily on your background and time): one file every three to six weeks, with two or three sessions per week of reading plus exercises, and a capstone project every four to five files. The whole sequence is then a project of roughly a year or more at a few hours per week. Keep the notebook habit; retention comes from applying the material to your own systems.
